# Live finding — 2026-07-24 dev-host upgrade

## Hermes config re-serialization destroys the owned marked block

Reproduced on the development host during the 0.2 dev install. Installing
another Hermes plugin (`orca-status`, added 2026-07-22) caused Hermes to
re-serialize `~/.hermes/config.yaml`: the roundtable entry stayed enabled
exactly once, but the comment-fenced managed block recorded in
`harness-setup.json` no longer exists byte-for-byte. Every
`roundtable-setup` entry point — including read-only `status` — then fails
closed with the single line `managed Hermes plugin drift: exact marked
block is missing`, with no per-harness report and no remediation guidance.

Hermes rewrites its config on any settings change, so this will hit every
Hermes user who ever touches Hermes settings or plugins after onboarding.

Expected behavior:

1. `status` must stay a diagnosis surface: report the drift per harness
   (other harnesses still shown) instead of dying on the first check.
2. When the semantic state is intact (`roundtable` enabled exactly once,
   not disabled), offer explicit adoption: downgrade the ownership record
   to a pre-existing entry (`enabled_added: false`,
   `managed_fragment: null`) rather than requiring a hand edit of
   `harness-setup.json`.
3. Reconsider fencing YAML that a harness re-serializes; exact-byte blocks
   may only be viable for files Hermes never rewrites.

Recovery performed today (expert path, documented here for reproducibility):
manifest backed up to `~/Documents/Workspace/backups/`, then
`harnesses.hermes.config` edited to `enabled_added: false`,
`managed_fragment: null`; `status` and `apply` proceed afterwards.
