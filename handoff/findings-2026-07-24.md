# Live findings — 2026-07-24 dev-host upgrade

## Orphaned runtime project record blocks the coordinated reload as "ambiguous"

Reproduced on the development host. The Build Week demo stage
`~/Demo/rt-demo` was deleted after filming, but its host runtime record
(`~/.roundtable/.runtime/projects/<hash>/` with `project.json` and two old
seat leases) survived. `inspect_host_harness_seats` canonicalizes every
recorded `projectRoot` with strict resolution, so the ENOENT raised a
`RuntimeStateError`, `_reload_status` classified the whole host lease
state as ambiguous, and the launcher preflight refused the app-server
reload indefinitely (`reload_deferred_busy`). The demo used an isolated
`RT_PROJECTS_FILE` registry, but host runtime state under `.runtime/` is
shared — the isolation boundary does not cover it.

Expected behavior:

1. A lease record whose project root no longer exists is a determinate
   orphan, not ambiguity: classify it as orphaned, name the offending
   record in the diagnostic, and stop letting it block a reload.
2. `roundtable doctor` should surface orphaned runtime records with a
   cleanup affordance instead of leaving them to hand inspection.

Second specimen, same session: after the orphan was cleared, the retry
failed on the next record — `e2601c50…`, an incomplete Build Week record
(created 2026-07-21 12:51) with no `project.json`, no `lease.json`, and
directory mode 0755, rejected as `runtime path exposes group/other
permissions`. Two additional expected behaviors:

3. The scan fails closed on the first invalid record, so the operator
   discovers blockers one retry at a time; a single pass should
   enumerate every invalid record.
4. `roundtable doctor` maps the stale wake-bridge fingerprint FAIL to
   the wrong fix (`install a Codex release at or above the floor`); the
   remedy for a stale bridge build is the coordinated reload. Fix-hint
   mapping regression from the 2026-07-24 probe rewrite.

Recovery performed today: both record directories were moved to
`~/Documents/Workspace/backups/`; a full-tree audit (group/other bits,
missing `project.json`) found no further invalid records, and
`inspect_host_harness_seats("codex")` then completed with only a
non-blocking `stale` Build Week seat.

## Hermes config re-serialization destroys the owned marked block

Reproduced on the development host during the 0.2 dev install. Installing
another Hermes plugin (`orca-status`, added 2026-07-22) caused Hermes to
re-serialize `~/.hermes/config.yaml`: the roundtable entry stayed enabled
exactly once, but the comment-fenced managed block recorded in
`harness-setup.json` no longer exists byte-for-byte. Every
`roundtable-setup` entry point — including read-only `status` — then fails
closed with the single line `managed Hermes plugin drift: exact marked
block is missing`, with no per-harness report and no remediation guidance.

Hermes rewrites its config on any settings change, so this will hit every
Hermes user who ever touches Hermes settings or plugins after onboarding.

Expected behavior:

1. `status` must stay a diagnosis surface: report the drift per harness
   (other harnesses still shown) instead of dying on the first check.
2. When the semantic state is intact (`roundtable` enabled exactly once,
   not disabled), offer explicit adoption: downgrade the ownership record
   to a pre-existing entry (`enabled_added: false`,
   `managed_fragment: null`) rather than requiring a hand edit of
   `harness-setup.json`.
3. Reconsider fencing YAML that a harness re-serializes; exact-byte blocks
   may only be viable for files Hermes never rewrites.

Recovery performed today (expert path, documented here for reproducibility):
manifest backed up to `~/Documents/Workspace/backups/`, then
`harnesses.hermes.config` edited to `enabled_added: false`,
`managed_fragment: null`; `status` and `apply` proceed afterwards.
