# Roundtable 0.2 — Competitive decision document

Evidence base: six lens reports plus one independent verification pass. Verification refuted or narrowed six claims; those are corrected below and the refuted versions are not carried forward. Two builds of Orca are in play throughout — the installed **1.4.150** (orchestration schema v6) and source **HEAD 1.4.160-rc.2** (schema 17, the Run/Delivery layer landed 2026-07-27 and has not shipped). Warp evidence is now source-grade: Warp is open source (AGPL-3.0/MIT dual, Denver Technologies), so `strings`-derived Warp claims from two lenses were re-derived against the tree and corrected where they disagreed.

### Corrections to the brief's premises

Four assumptions in the tasking are wrong or overstated and should not survive into the design conversation:

1. **"Warp is closed-source Rust."** It is open source. Every Warp claim above is file-level.
2. **"Orca rewrote `~/.claude/settings.json` and broke Roundtable."** It rewrote it, but additively. Roundtable's `rt-wait-inbox` entries are intact in both `SessionStart` and `Stop`, sitting alongside Orca's ten entries. Orca sweeps only its own entries, matched by script filename.
3. **"Orca broke Roundtable's byte-fenced Hermes block."** Largely misattributed. The `.bak` Orca itself copied immediately before its own write already had 2 comment lines where the 2026-07-07 backup had 21 — roughly 19 of 21 comments were gone before Orca ever touched the file. Roundtable's own `handoff/findings-2026-07-24.md` names the cause: Hermes re-serializes its own config on any settings change. And `harness-setup.json` currently shows `"managed_fragment": null` — Roundtable owns no fenced block there today. Orca's YAML round-trip is real and finished the job; it is not the cause.
4. **"Warp built our design and rejected it in production."** The DDL is real (`2026-02-28-030000_add_orchestration_messaging` creating `orchestration_events(... delivered INTEGER DEFAULT 0)` and `orchestration_messages(... address_agent_ids ...)`, dropped 23 days later). But the public repo history is squashed to a single commit dated after the deletion, and zero non-migration source references survive. **We can say the schema existed and was deleted. We cannot say it ran, or why it was deleted.** Do not build a strategy on the counterfactual.

One additional correction with design consequences: the claim that Warp isolates concurrent Claude children by giving each its own `CLAUDE_CONFIG_DIR` is **refuted for the desktop app**. Every reference in the tree is a read; the per-task directory is set by the Oz *cloud* worker (`plugin_manager/claude.rs:350-353`). Warp's local children share `~/.claude`. There is no verified desktop prior art for per-child config-dir isolation of Claude — only Orca's shadow `CODEX_HOME` for Codex.

## 2. Why Roundtable cannot do worktrees today

The mailbox's *location* and the project's *identity* are the same object, and both are the cwd. `find_project_root()` walks upward from `os.getcwd()` for `.roundtable/agents.yaml` (`_rtlib.py:362-388`); the maildir is then a child of whatever that walk found (`rt-say:24`, `INBOX_DIR = <root>/.roundtable/inbox`); the host runtime seat directory is `sha256` of that same resolved path (`_rtruntime.py:190-192`); and `rt-wait-inbox._project_root()` goes further, **rejecting an explicitly injected `RT_PROJECT_ROOT` that disagrees with the cwd-discovered project** (`rt-wait-inbox:77-93`) — so identity cannot be overridden from the environment even when the launcher owns the exec. A second worktree is a second resolved path, therefore a second hash, a second `.roundtable/` tree, a second `agents.yaml`, and a disjoint namespace with no parent object relating them; and since `rt-say <agent> <kind> <body>` has no project component in its grammar, there is no slot in the address to put a sibling worktree even if a relation existed. The multi-instance half is a much smaller problem wearing the same clothes: `configured_target` already resolves `claude-fe` to its own instance and `publish_maildir` already writes `inbox/claude-fe/new`, and `rt-say` already errors `"has multiple instances; use one of:"` — the naming, routing and storage layers are done. What refuses is one predicate in `claim()`: `same_harness = record["harness"] == harness` → `SeatOccupied` (`_rtruntime.py:861-865`). **These are two independent defects, and only one of them is architectural.**

Concretely on this machine: `~/Code/roundtable-product` is already a linked worktree of `~/Code/2026-OAI-Build-Week`. `git rev-parse --path-format=absolute --git-common-dir` returns the same `~/Code/2026-OAI-Build-Week/.git` from both checkouts. A stable, git-native repo key that all worktrees agree on already exists and costs one subprocess call.

## 3. What Orca and Warp pay for their flexibility

**Orca pays a running Electron app.** The CLI is a pure RPC client — `grep -rn 'OrchestrationDb|orchestration.db|sqlite' src/cli/` returns nothing outside tests. With the app closed, `orca-runtime.json` is absent and every orchestration command returns `runtime_unavailable`. There is no filesystem fallback and no enqueue path: a cron job, a git hook, a CI step or a script cannot leave a message for an agent. Its wake is bracketed-paste keystroke injection into the PTY followed by a `\r` written on a 500 ms timer, with `delivered_at` stamped only if that Enter lands — the code carries a comment explaining that Claude Code treats a large PTY write as a paste and swallows the `\r`. Work in flight is bound to a `term_<uuid>` that is cleared on every renderer reload; a message addressed to a handle whose pane died stays undelivered forever with no re-addressing to a replacement agent. Its hook channel authenticates with one host-wide bearer token minted per app launch, and every identity field in a hook POST is self-asserted by the poster. And its own engineers treat orchestration as a minority feature they optimize *around*: the DB is created lazily for all users with an emptiness cache to short-circuit a per-terminal fan-out.

**Warp pays a network and an account.** The addressable identity does not exist until Warp's server issues it; a local child pane cannot be launched without a server round trip. Two agents in two panes of the same window message each other through `app.warp.dev` with a 15-second timeout. The local-transport enum variant exists as dead code. The one local primitive — `wait_for_events` — is a blocking receive whose watchdog logs `"dropping pending entry"` when the recipient stops waiting, so a message delivered while the recipient is between turns is simply lost. Restart replay of agent events was documented as broken in their own spec. The scriptable local surface that would fix this, `warpctrl`, is feature-flagged off on every public channel and its wrapper is not in the shipped bundle; and even when enabled it deliberately refuses to provide an action that submits input. Offline or logged out, Warp is a very good terminal with zero multi-agent capability.

**Both pay the same structural price: the seat exists because a pane exists.** Pane-keyed identity is genuinely better than path-keyed identity for multi-instance and worktrees, and both products get those capabilities essentially free. What it costs is every consumer that is not a window: scripts, schedulers, hooks, other machines, and the recipient's own future self after a crash. **Copy the decoupling — an allocated identity with the path demoted to an attribute. Do not copy the hosting (a UI process as the identity registry) or the wake (keystroke injection, cloud bus).**

## 4. Design options for 0.2

**Option A — Delete the harness gate; make the seat per-instance.**
*Mechanism:* replace `same_harness` with `same_agent` in `claim()` (`_rtruntime.py:861-865`) so the uniqueness key becomes `(project, agent_instance_id)`. `agents.yaml` already declares `instances`; `configured_target`, `publish_maildir` and `rt-inbox` already key on the instance. Add per-seat `CLAUDE_CONFIG_DIR` at launch **only if experiment 1 below shows real contention**.
*Cost:* one predicate plus tests, if contention is not real. Days, not weeks, if it is.
*Breaks:* nothing for single-instance users — the declared-instance path is already live. Error messages change from `SeatOccupied` to nothing for the two-Claude case.
*Preserves:* offline durability untouched; fenced identity untouched (leases are already per-agent directories under `agents/<sha256(agent_id)>/`).
*North star:* excellent. Zero migration, invisible to non-experts.
*Does not solve worktrees.*

**Option B — A repo group above the project, keyed on the shared git dir. (Keeps path identity.)**
*Mechanism:* keep `project_hash = sha256(path)` exactly as is. Add an optional `repo` field to entries in the existing host registry `~/.roundtable/projects.yaml` (which already has a lock and a schema), computed at `roundtable init` / registration time as `git rev-parse --path-format=absolute --git-common-dir`. All worktrees of one repo land in one group by construction. Extend the address grammar additively: `rt-say <agent>@<sibling> <kind> <body>`, where `<sibling>` resolves through the group to a registered project root; delivery is the same tmp→new atomic rename, into *that* project's maildir. Record the origin project in the envelope. Fail closed when the target root is unregistered, outside the group, or lacks the named agent in its own `agents.yaml`.
*Cost:* moderate. Touches the registry schema, `rt-say` target resolution, `rt-inbox` display (show origin), `roundtable init`, and the doctor. No change to `claim()`, the runtime layout, the hooks or the Codex bridge.
*Breaks:* nothing. `rt-say claude ...` is unchanged; the `@` form is new syntax.
*Preserves:* offline durability fully — a cross-worktree send is still just a file write, with no live process on either side. Fenced identity mostly: the one new question is that a fenced seat now writes outside its own `RT_PROJECT_ROOT`, which `require_fenced_seat` currently treats as an invariant. Mitigation is the group membership check plus an envelope origin field; this is a real review item, not a footnote.
*North star:* very good. Non-experts never see it; worktree users type one extra token.

**Option C — Allocated seat id; path demoted to an attribute. (The Orca/Warp shape.)**
*Mechanism:* mint an opaque seat id at `claim()`, stamp it into the harness env at launch (`RT_SEAT_ID`), key the runtime record on it, and keep cwd inference as a convenience alias that resolves to an explicit id before any operation — Orca's own discipline (`selectors.ts:23-80`, which resolves `current` to a concrete `id:` immediately because cwd is ambiguous).
*Cost:* rewrite. Every `rt-*` tool, the lease format, the three harness adapters, the Codex launchd bridge, `rt-doctor`, plus a migration for existing runtime records — and the orphaned-runtime-record blocker already on file says migrations here are not cheap.
*Breaks:* the guarantee that `RT_PROJECT_ROOT` must match cwd (`rt-wait-inbox:77-93`) becomes wrong and must be replaced by a seat-id check. Every existing seat must be re-claimed.
*Preserves:* offline durability **only if the mailbox stays project-local**. If the mailbox follows the identity host-global (Orca's shape), we lose "the mail lives with the repo", which is the property that makes a Roundtable project portable and inspectable.
*North star:* fails it. Correct in the abstract, wrong for this release.

**Option D — A worktree launcher and nothing else. (Warp's actual answer.)**
*Mechanism:* `roundtable worktree <name> --agent claude` → `git worktree add`, `roundtable init` in the new checkout, register it, launch the seat there. Optionally copy/symlink `.env`-class files the way Orca's `.worktreeinclude` does.
*Cost:* small. One new subcommand over existing primitives.
*Breaks:* nothing.
*Preserves:* everything.
*North star:* excellent, and it is the half of the operator's request that is actually about isolation rather than routing. It does not give cross-worktree routing at all.

**What I would pick: D, then A, then B — and explicitly not C.**

D first because it is a day of work and delivers the isolation the operator described without touching a single architectural fact. A second because deleting one predicate is the entire remaining distance to individually addressable same-harness instances, and shipping the P0 cut into 0.2 when the naming and storage layers already support the plural case is indefensible. B third as the architectural core: it is the only option that creates a route between worktrees while preserving the one property neither competitor has and neither can cheaply acquire — that writing the file *is* delivery, with nothing running. C is the design both competitors converged on, and it is right, and it costs a rewrite for a capability that B delivers additively; revisit it only if cross-host transport is promoted from roadmap to committed.

Two things worth stealing regardless of option, both cheap: Orca's version-matched skill guide (the on-disk `SKILL.md` is a stub that tells the agent to run `orca skills get orchestration` so the contract can never drift from the binary that executes it — we have already been bitten by marked-block drift), and Warp's `OZ_PARENT_MAX_CONTEXT_CHARS` context budget with an explicit "more messages remain queued" deferral, which our drain currently lacks and which will matter the moment several worktree seats message one lead.

## 5. The positioning opening

**Orca cannot serve a request when its window is closed.** Its CLI has no database access by construction; the coordination substrate lives inside an Electron main process. Anything that must work from cron, a git hook, CI, a headless box, or a machine where the user quit the app is out of reach without inverting the architecture. **Warp cannot serve a request without an account and a network round trip**, because the address itself is issued by their server; its local transport is a dead enum variant and its local-only scriptable surface is feature-flagged off on every public channel.

That is the opening, and it is exactly one sentence wide: **`rt-say` succeeds when nothing else is running, across three different harnesses, with no account.** Everything else on our list, they have or can get. Orca already ships cross-worktree group addressing (`@worktree:<id>`), a 3-factor capability fence, an at-least-once batch-replay-until-ack delivery contract, a 216-command CLI, an editor with a review loop, and cross-machine federation. Warp already ships worktree ergonomics, a real IDE surface, and a cloud tier. Neither is structurally blocked from adding a local durable queue — Warp had one and dropped it, Orca has the SQLite file and simply chose not to let the CLI open it. Both decisions are reversible in an afternoon.

Be skeptical about the moat's durability for a second reason: two independent, better-funded teams routed around offline durable local delivery. Orca's own comment notes the orchestration DB is created for all users but only a small minority ever dispatch. Anthropic is commoditizing the intra-harness case directly — Orca now *hosts* Claude Code's Agent Teams by emulating tmux 3.4 (`claude-agent-teams-service.ts:23-72`), which means "many Claudes talking to each other" is becoming a harness feature, not a product. **The defensible position is not multi-agent coordination. It is cross-harness, no-daemon, no-account, durable-on-disk coordination that a non-expert can install in five minutes** — and the honest framing is that this is a narrow, real, and time-limited advantage, not a category.

## 6. What remains unknown, and the cheapest experiment

1. **Do two concurrent Claude Code processes in one directory actually conflict?** This decides whether Option A is one line or a config-dir subsystem — and whether our P0 cut was defending against a problem that does not exist. *Experiment: scratch repo, two Claude Code sessions, both editing and both writing history; watch `~/.claude` for clobbering. 15 minutes.* Do this first.
2. ~~Is `git rev-parse --path-format=absolute --git-common-dir` stable across bare repos, submodules and `--separate-git-dir`?~~ **Settled 2026-07-28: yes, and no fallback is needed.** Six cases in a scratch tree:

| case | key | verdict |
|---|---|---|
| ordinary repo | `main-repo/.git` | baseline |
| linked worktree | `main-repo/.git` | groups with its repo |
| submodule | `main-repo/.git/modules/vendor` | own key, correctly separate |
| `--separate-git-dir` | the real git dir, not the worktree path | tracks the repository object, not the location |
| bare repo | `bare.git` | fine |
| worktree of a bare repo | `bare.git` | groups with the bare repo |

   The submodule result is the desired behaviour rather than a gap: a submodule is its own
   repository and its agents should not silently join the parent's group. The
   `--separate-git-dir` result matters more than it looks — the key follows the repository
   object, so it survives moving a worktree. The bare-repo pair means the
   `clone --bare` plus several worktrees layout is supported for free.
3. **Does a cross-project fenced send violate a real invariant, or only a conservative one?** *Experiment: read `require_fenced_seat` and `rt-wait-inbox._project_root()` together and write the threat statement — one hour, no code.*
4. **Orca's Run/Delivery layer in practice** — ack semantics, the one-outstanding-batch fence, `--wait` behaviour. Unshipped and unobservable here. *Experiment: throwaway macOS account, `ORCA_USER_DATA_PATH` to a scratch dir, install 1.4.160-rc.2+, run `run-create` / `worker-start`, read the DB and socat the socket. 30 minutes, not safe on this machine.*
5. **Whether Orca's `::workspace:<uuid>` multi-instance path can ever be reached for a git repo.** Verification found it gated to folder projects; a partial path would change how we read their worktree model. *Experiment: grep every caller of `getFolderWorkspaceInstanceId` and `FOLDER_WORKSPACE_INSTANCE_SEPARATOR` for a non-folder repo. 30 minutes.*
6. **Whether an Orca message bound to a dead handle is ever re-addressed.** *Experiment: read `lifecycle-reconciliation.ts` plus the `retryOf` flow. One hour.*
7. **Whether Warp's deleted orchestration tables were ever wired to code.** Unanswerable from a squashed history. *Experiment: GitHub code search across the `warpdotdev` org (`oz-agent-worker`, SDKs) for `orchestration_messages` / `address_agent_ids`. 20 minutes.* Until then, do not cite the deletion as a verdict on our design.
8. **Whether Warp can enable `warpctrl` on Stable remotely** (server-delivered experiment flags exist). Would change how fast the headless-addressing gap closes. *Requires a running Warp and a network capture — not worth it now.*
9. **Whether Roundtable should own a fenced block in `~/.hermes/config.yaml` at all**, given Hermes re-serializes its own config and currently `managed_fragment` is null. *Experiment: scratch `$HOME`, plant a comment fence, toggle one Hermes setting, see if it survives. 20 minutes.* If it does not, move Hermes ownership to a separate included file or a provenance-carrying key and stop depending on comment markers.
10. **Whether Warp's server permits addressing a non-descendant agent** (their docs say the agent id is the only address that matters; the tool surface only ever hands out child ids). Requires a login; declined under the constraints. **Report as unknown.**
