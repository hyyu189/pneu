## 1. Systemic diagnosis

Three design gaps generate essentially every defect below. They are not independent — (P1) creates the garbage, (P2) prevents anyone from seeing it, (P3) makes the eventual symptom point somewhere else.

### P1 — State is armed with a fence and disarmed by nothing

Every session-scoped object in the runtime has a rigorous, atomic, identity-checked *creation* path and no owner responsible for its *end*:

- `release()` (`bin/_rtruntime.py:1360`) has no production caller anywhere in `bin/` or `roundtable_packaging/`; no `SessionEnd` hook exists in the tree; `rt-wait-inbox`'s `finally` (`bin/rt-wait-inbox:342-352`) calls `clear_wake()`, which pops only `watcherPid`/`heartbeatAt` (`bin/_rtruntime.py:1332-1334`).
- `arm_codex_launch_intent` has exactly one call site (`bin/_rtlauncher.py:532`) and no renewal, no expiry sweep, and no unlink.
- Wake bindings are removed only by an explicit operator `unbind` or a competing `bind`; no code path evicts a binding whose fence check has failed permanently.
- Installed version trees are unioned, never pruned (`roundtable_packaging/cli.py:752-753`).
- Four launchd sinks and one JSONL event log append forever; `grep -rn 'rotat|maxBytes|st_size' bin/` returns no rotation logic.

The consequence is not primarily disk: it is that *stale state is indistinguishable from live state to every consumer*, so the ambiguity edges (`SeatAmbiguous`, `RuntimeStateError` on a vanished `projectRoot`, a binding to a dead thread) all become reachable through ordinary use.

### P2 — Health checks iterate over what is present, so absence is structurally invisible

Every green-while-dead state in this audit has the same shape: the check's iteration source is the artifact that exists, so the failure mode — the artifact *not* existing — can never produce a line.

- `hook_trust` (`bin/rt-doctor:478-511`) and `_hook_trust_gate` (`bin/rt-codex-wake:1515-1562`) iterate the `hooks/list` response, `continue` past anything `enabled: false`, and classify only `trustStatus`. Neither ever matches on `<prefix>/bin/rt-codex-session-start`. `enabled_count == 0` renders as `OK … has 0 enabled hook(s), all managed or trusted`.
- `codex_anchor` (`bin/rt-doctor:1133-1294`) iterates `bindings` only; `codex_instances`/`inspections` are consumed but never scanned for the missing-binding direction. Three live unbound Codex seats therefore produce **zero** anchor lines.
- Seat enumeration is registry-driven (`bin/rt-doctor:1106` → `inspect_project_seats`); `inspect_host_harness_seats` (`bin/_rtruntime.py:736`, whose own docstring says the registry "can be incomplete") is never imported by doctor. Live: 6 runtime project records vs 12 registry entries.

Operationally: **doctor's OK lines are not evidence for the README's Codex wake claim.** The 07-27 outage passed doctor cleanly not by accident but by construction.

### P3 — Error information is collapsed onto the success or benign channel at the boundary

- `rt-wait-inbox` returns exit 2 — Claude's "you have mail, wake up" signal — from the mail branch (`:334-338`), the usage-error branch (`:409`), *and* the catch-all exception branch (`:419-421`).
- The wake bridge's startup discovery failure returns exit `0` under `KeepAlive: {SuccessfulExit: false}` (`bin/rt-codex-wake:2278-2283`, `bin/_rtcodex.py:314`) — a hard failure encoded as "job completed successfully".
- `project_config_has_codex` (`bin/rt-codex-wake:884-895`) returns a bare `False` for five distinct misconfigurations, consumed as a silent boolean filter at `:2164` with no `project_skipped` event.
- `vacant` (idle) and `stale` (dead owner) share WARN and share the fix hint `launch a seat` (`bin/rt-doctor:873-878`).
- A permanently-failing binding check logs an identical full record every 5.1 s with no dedup, backoff, or eviction, diluting the real signal ~30:1.

And where the signal does survive, the remedy is wrong: `restart the wake adapter for codex` for an unbound seat (filed 07-27); `roundtable setup apply` for an ownership-drift FAIL whose first action re-runs the validation that failed (`bin/rt-doctor:156-162`, `:189-197` → `roundtable_packaging/setup.py:2542-2548`, before any mutation, with no `adopt` branch anywhere).

### Scope note — an expired design premise

`bin/_rtcodex.py:72` hardcodes `DEFAULT_SOCKET = ~/.codex/app-server-control/app-server-control.sock` — Codex's *own* canonical managed-daemon path — and ships a `KeepAlive: True` LaunchAgent binding it. `handoff/archive/codex-seat-lifecycle-2026-08-04.md:12` records the rationale: "The npm Codex installation cannot use `codex app-server daemon start`." That premise died at the standalone switch. Standalone `0.145.0` ships `daemon bootstrap|start|restart|stop|enable-remote-control`, and `codex app-server daemon version` now reports Roundtable's process as Codex's managed daemon.

## 2. Merged findings, by severity then blast radius

Lens attributions in brackets. Items marked ⟡ deepen an already-filed finding rather than adding a new one.

### F1 — HIGH · `rt-wait-inbox` returns the Claude wake code for every error, and the anti-loop guard is unreachable on the error path
*[cross-harness]* · blast radius: every Claude seat on every host

`bin/rt-wait-inbox:334-338` returns `2 if claude_hook else 0` on mail; `:409` returns 2 on usage error; `:419-421` returns 2 from `except (FenceRejected, RuntimeStateError, OSError)`. Byte-identical signals. The loop brake (`stop_hook_active` + same generation + `wake_attempts >= 2`) is at `:206-227`, *after* `_project_root()` (`:197`), `_lease_environment()` (`:198`) and `load_validated_lease()` (`:200`) — it requires the very lease those lines fail to produce.

Both owned Claude groups carry `asyncRewake` (verified in live `~/.claude/settings.json` and `roundtable_packaging/setup.py:741-760`). Cheapest trigger needs no exotic configuration: **a second roundtable-launched Claude seat in the same project supersedes the lease**, so the older session's `load_validated_lease` raises `FenceRejected` on every Stop → exit 2 → wake → turn ends → Stop → repeat. A nested `claude` launched from a subdirectory of a live seat hits `bin/rt-wait-inbox:86-89` identically. Contrast `integrations/hermes/roundtable/__init__.py:311-345`, which classifies waiter output by explicit markers and terminates cleanly with `_FENCE_MESSAGE` on exactly this condition.

The user pays for model turns in a session that provably cannot receive mail. Unverified link: whether Claude Code itself caps `asyncRewake` exit-2 (see §5.6) — if it does, the cost bound shrinks but the signal collision remains.

**Fix:** return the wake code only from the mail branch; stderr + `return 0` on `:409` and `:419-421`. Move a lease-independent brake ahead of the failing calls, or record failures host-locally (project + agent + reason + count) so doctor can report a persistently failing watcher.

### F2 — MEDIUM · `hook-trust` never asserts Roundtable's own hook is present and enabled, in *both* the doctor probe and the live wake gate
*[doctor, cross-harness, codex-bind — three lenses, one defect]* · blast radius: the entire Codex wake precondition

`bin/rt-doctor:478-511` and `bin/rt-codex-wake:1515-1562` share the omission (doctor's docstring at `:409` says it deliberately mirrors the gate). Both skip `enabled: false` entries and blocklist only `untrusted`/`modified`. Neither matches on command path or an owned key. `enabled_count` is interpolated unguarded, so a globally disabled hooks feature yields `OK … has 0 enabled hook(s), all managed or trusted` while hook delivery is dead host-wide.

Live composition of `~/.codex/hooks.json`: 13 enabled entries — 11 cmux/orca, one cmux-gated `rt-startup-advisory`, and exactly one owned entry (`SessionStart[2]`, command `~/.roundtable/bin/rt-codex-session-start`, matcher `startup|resume|clear`). Doctor prints the OK line for all 12 projects.

Two scope corrections against earlier drafts: hook **deletion** *is* caught, by a different check — `report_codex_setup` → `_validate_codex` → `roundtable_packaging/setup.py:1810-1826` raises on `groups.count(group) != 1` and surfaces as `FAIL codex-setup`. And this is **not** why the 07-27 outage passed doctor: `hooks/list` genuinely returned the hook `enabled: true, trustStatus: trusted`. The residual holes are (a) registered-but-disabled, (b) zero-enabled rendered as OK.

Secondary, plausible but unproven: the FAIL branch (`:499-506`) fires `wake is blocked pending hook review` when any *unrelated* cmux hook goes untrusted after an upgrade, sending the operator to `/hooks` for something unrelated to Roundtable. Requires knowing Codex's per-hook trust semantics (§5.4).

**Fix:** fix once in `_hook_trust_gate` and let doctor keep mirroring — require ≥1 enabled entry whose command resolves to `<prefix>/bin/rt-codex-session-start` with `trustStatus ∈ {managed, trusted}`; absence (including empty list) is a distinct reason `roundtable_hook_not_enabled`. Report foreign untrusted hooks as a separate informational line.

### F3 — MEDIUM · Wake-bridge startup: a discovery error exits 0 and is never restarted; a YAML parse error anywhere in the registry crash-loops the bridge host-wide
*[observability, failure-modes — merged, with the second half found only on re-verification]* · blast radius: all Codex messaging on the host

`bin/rt-codex-wake:2278-2283`: `except (IdentityError, OSError) … return 1 if args.once else 0`. The daemon path (no `--once`, `bin/_rtcodex.py:286-292`) returns 0; the polarity is inverted relative to the debug path. `bin/_rtcodex.py:314` sets `KeepAlive: {SuccessfulExit: False}`, confirmed live (`plutil -p ~/Library/LaunchAgents/com.roundtable.codex-wake.plist` → `SuccessfulExit => false`, `ThrottleInterval => 5`).

Two distinct outages from one bad project:

- **(a) OSError at startup** → exit 0, launchd considers the job done, Codex wake is dead host-wide. Trigger is narrower than first claimed: `load_project_registry` (`bin/_rtlib.py:151-154`) already drops entries whose `.roundtable/agents.yaml` fails `is_file()`, and an unresolvable root is caught as `IdentityError` → `continue` at `bin/rt-codex-wake:700-711`. What survives is an `agents.yaml` that exists but fails `open()` — mode 000, an I/O error, or a TOCTOU delete. Note this is an *inconsistency*, not a policy: the mid-run re-discovery at `:2330` sits inside `except (OSError, TimeoutError, CodexRuntimeError)` at `:2352` and retries with backoff — the live log holds **2,965** `bridge_connection_error` records proving that path works.
- **(b) YAMLError** — `load_agents_doc` (`bin/_rtlib.py:392-396`) calls `yaml.safe_load`; `yaml.YAMLError` is neither `OSError` nor `IdentityError` and appears in none of the three handlers (`:2282`, `:2354`, `:2445`). `is_project_root` only stats, never parses. One hand-edited broken `agents.yaml` in any registered project ⇒ uncaught traceback, exit 1, relaunch every 5 s, re-read the same broken file: a permanent throttled crash loop killing wake for every project.

Neither has fired here (`bridge_disabled` count: **0** in the full 94,145-line log; `rt-codex-wake.stderr.log` is 0 bytes, mtime 2026-07-16 — and no tool in `bin/` reads it).

**Fix:** make discovery fault-isolating — wrap the per-project `project_config_has_codex` call at `:2164` in the same per-path try as `canonical_project`, catching `yaml.YAMLError` and `OSError`, logging `project_config_unreadable`, and continuing. Then drop the special-case return at `:2282` and fall through to the run loop with whatever survived; the registry-stamp refresh at `:2326-2331` picks up projects later. Reserve exit 0 for signal-initiated shutdown. Have doctor tail `rt-codex-wake.stderr.log` and the last `bridge_disabled` record when the bridge is down.

### F5 — MEDIUM ⟡ · The Codex launch intent is a one-shot 300 s token with no renewal path, and `clear` cannot rescue it
*[cross-harness]* · this is why the three live seats sat dead for days rather than self-healing

`resolve_codex_launch_intent` (`bin/_rtruntime.py:975-1055`), unclaimed branch `:1042-1048`: if `active is None`, return `None` when `source ∉ {startup, resume}`, then return `None` when `age > ttl` (`DEFAULT_CODEX_LAUNCH_INTENT_TTL = 300.0`, `bin/_rtruntime.py:29`). So `/clear` on an unclaimed intent is rejected by the source test and a late resume by the age test — the intent is inert forever, and nothing ever re-arms `armedAt` (single call site, `bin/_rtlauncher.py:532`).

Live, all four intents `activeNativeSessionId: null`, `lastSessionStartAt: null`:

| project | armedAt | seat pid | alive |
|---|---|---|---|
| `~/quant` | 2026-07-25T23:07:06Z | 84092 | yes |
| `~/MoneyMarket-MacroFinance` | 2026-07-25T23:07:50Z | 84876 | yes |
| `~/Code/roundtable-product` | 2026-07-25T23:08:06Z | 85210 | yes |
| `~/Code/2026-OAI-Build-Week` | 2026-07-21T22:41:10Z | 50900 | **dead** |

The asymmetry with Claude/Hermes is structural, not sloppiness: Codex hooks are executed by the launchd app-server, which cannot inherit the launcher's `RT_*` fence the way `bin/_rtlauncher.py:234-241` gives it to the other two. The intent file is the substitute — but the substitute has no renewal.

Scope: "permanently unbindable" overstates it — manual in-turn `rt-codex-wake bind` still works (already recorded in `findings-2026-07-27.md:131-133`), and the observability half is filed as expected-behavior item 1 there. The **new** content is the mechanism.

**Fix:** allow renewal, not just better reporting. While the seat owner PID is alive and the intent names the current fenced lease, let the launcher or the bridge sweep refresh `armedAt`; or accept a late `startup`/`resume` whose intent resolves to the still-current active lease. The fence — lease revision + owner identity — is what prevents an unrelated native Codex in the same cwd from stealing the seat; the clock is not load-bearing for safety.

### F6 — MEDIUM · Roundtable's LaunchAgent owns Codex's canonical managed-daemon socket, so Codex's own documented daemon commands collide with it
*[codex-bind]* · fails closed, but with a misleading remedy and no documentation

`bin/_rtcodex.py:72` (socket constant), `:262-272` (LaunchAgent running `codex app-server --listen unix://<that path>`, `KeepAlive: True`, `WorkingDirectory: $HOME`). Live: pid 73899, ppid 1, `~/.codex/packages/standalone/current/codex app-server --listen unix://~/.codex/app-server-control/app-server-control.sock`. `codex app-server daemon version` returns `{"status":"running","managedCodexPath":"…/standalone/current/codex","socketPath":"…/app-server-control.sock","appServerVersion":"0.145.0"}` — Codex believes our process is its managed daemon. Codex's own locks (`~/.codex/app-server-daemon/{daemon.lock,app-server.pid.lock}`, both dated 2026-07-15) are not held by 73899. Host is multi-tenant (ChatGPT.app app-server, pid 4075).

A user or first-party client running `codex app-server daemon restart|stop` fights `KeepAlive: True`; whichever rebinds last strands the other on a stale inode. It does fail closed — `require_pid_lineage` (`bin/_rtcodex.py:1907-1928`) authenticates the socket peer and errors with `Unix socket peer is not owned by the Roundtable LaunchAgent process tree` — but no doc, README row, or doctor item tells anyone that Roundtable, not Codex, manages that path.

**Fix:** now that standalone is the supported distribution, either adopt the managed daemon (`daemon start` / `enable-remote-control`) and retire the competing LaunchAgent, or move to a private socket path and drop the `daemon version` call that implies ownership. Either way: a doctor item naming the conflict when the socket peer is not the Roundtable launchd pid, plus corrections to `handoff/archive/codex-seat-lifecycle-2026-08-04.md:12` and the README Codex row.

*[lifecycle — significantly narrowed from the original claim]*

Confirmed: `release()` uncalled, no SessionEnd hook, `clear_wake()` does not remove the lease. Live: 11 `lease.json` under `~/.roundtable/.runtime/projects/`, **5 with dead ownerPid**, all claimed 2026-07-21:

| project | agent | ownerPid | claimedAt |
|---|---|---|---|

| `~/Code/rt-naive-test` | claude | 66109 | 2026-07-21T09:49:37Z |

| `~/Code/2026-OAI-Build-Week` | claude | 50781 | 2026-07-21T22:40:50Z |

All five verified absent from the process table. Doctor renders exactly those five as `status=stale` WARN with fix hint `launch a seat`.

Two impact claims from the original **refuted** and corrected: records do *not* accumulate monotonically — `claim()` (`bin/_rtruntime.py:882-899`) overwrites any non-active lease in place, so the count is bounded by (project × agent) pairs ever used, and relaunching silently reclaims. A `stale` lease blocks nothing — `_reload_status` (`bin/_rtcodex.py:991-999`) treats only `active_healthy`/`active_unhealthy`/`ambiguous` as blockers. And plain same-user PID reuse yields `stale`, not `ambiguous`, because of the `ownerStart` fingerprint (`bin/_rtruntime.py:503-506`).

The real edge: `_owner_liveness` (`:487-508`) maps `os.kill` EPERM → `ambiguous`, so the failure needs the recorded pid reused by a process this user cannot signal (root-owned). Live-plausible here — the host is at pid 99739 in a wrapping ~99998 space with 211/1290 processes root-owned, and the counter demonstrably wrapped between 07-25 (pids 84876/85210) and 07-27 (pids 4570/9708/16183). When it lands, `claim()` raises `SeatAmbiguous`, the launcher refuses the seat (`bin/_rtlauncher.py:226-230`), and the host-wide Codex reload defers — until the colliding process exits. Transient, not permanent. Dead leases survive `roundtable-uninstall` (runtime preserved by default).

**Fix:** release the lease on clean exit (Stop-side for Claude/Hermes, exit path for the Codex launcher). Add an operator-facing reclaim (`roundtable seat release <project> <agent>`, or `doctor --reclaim`) so an ambiguity-wedged seat is recoverable without hand-deleting a SHA-256-named path. Make `_owner_liveness` distinguish "pid exists but belongs to another uid" from genuine ambiguity — a lease whose `ownerStart` cannot match a foreign-uid process is provably stale.

### F11 — LOW · doctor's WARN class is ~88% non-actionable, and exit code 0 does not distinguish "nothing running" from "running and unreachable"
*[lifecycle, doctor — merged]*

Reproduced live: **44 OK, 34 WARN, 0 FAIL, exit 0**. ## 5. What could not be determined, and the cheapest experiment for each

**5.1 — Why SessionStart is not dispatched for `--remote` threads under standalone 0.145.0.** Two live branches remain (per `findings-2026-07-27.md`): the app-server never dispatches because the thread is attributed to a non-interactive originator, or the hook runs and bails inside `resolve_codex_launch_intent` on the source/TTL guard. Both leave `lastSessionStartAt: null`. *Cheapest:* launch exactly one Codex seat via `roundtable codex` and read `<runtime>/projects/<hash>/codex-launch-intent.json` within 300 s. `lastSessionStartAt` non-null ⇒ the hook ran and the resolver rejected it (F5 is the whole story). Still null ⇒ the hook was never dispatched (an app-server attribution regression). One file read; one decisive bit. This is the highest-value experiment in the list.

**5.2 — Whether `rt-codex-wake unbind` genuinely fails to reach the running bridge.** `step()` reloads state from disk every iteration (`bin/rt-codex-wake:2120`) and `save()` adopts `disk_bindings` (`:179-195`), so the filed claim is mechanically surprising; the observed window was under two poll intervals. *Cheapest:* bind a throwaway project, run `unbind`, then watch `rt-codex-wake.log.jsonl` for ≥4 poll intervals (~21 s) *without* a kickstart. If rejections stop on their own, the filed item is an observation-window artifact and should be struck; if they continue, there is a second, unidentified persistence path.

**5.3 — Whether truncating a launchd-held stderr sink is clean.** Depends on whether launchd opens `StandardErrorPath` with `O_APPEND`. *Cheapest:* `lsof +fg -p 73899 | grep codex-app-server.stderr` and read the flag column; or truncate and compare `ls -ls` block count against byte size. Determines whether step 2 is safe as written or needs a daemon reload.

**5.4 — Codex 0.145.0's per-hook trust semantics: does one `untrusted` entry block the others?** Needed to confirm the F2 secondary claim that a cmux upgrade sends the operator to `/hooks` for an unrelated hook. *Cheapest:* copy `~/.codex` to a scratch `CODEX_HOME`, hand-edit one cmux hook's command to invalidate its `trusted_hash`, run `hooks/list` and one throwaway session against the copy, and see whether the roundtable hook still fires. Fully isolated; touches no live state.

**5.5 — Whether the phantom Build Week binding lived on disk for 5 days or only in the old bridge's memory.** `rt-codex-wake-state.json` has no history and the state file is not versioned, so this is unrecoverable after the fact. *Cheapest:* not an experiment but a code change — emit a `binding_evicted` / `state_reloaded` event with the binding key set on every `store.reload()` that changes `bindings`. ### New finding — a live Claude seat reports `active_unhealthy` between watcher generations, with the wrong fix

Observed in the diff, not caused by the cleanup. The `roundtable-product`
claude seat (owner pid 16183) moved `active_healthy → active_unhealthy`
during the run: its watcher (pid 16232) exited and its lease `wake` block
collapsed to `{"emptyBeats": 1}` — `clear_wake` popped `watcherPid` and
`heartbeatAt` (`bin/_rtruntime.py:1332-1334`) and nothing re-armed, because
the Stop hook that re-arms fires only at the end of a turn. A long turn
therefore holds the seat in `active_unhealthy` for its whole duration.

Delivery is not lost — the mailbox is durable and the next Stop-hook drain
collects it — so the cost is wake latency, not mail. The defect is the
report: doctor renders a normal mid-turn seat as unhealthy and prescribes
`restart the wake adapter for claude`, when there is no adapter to restart
and the correct answer is to wait for the turn to end. This is the same
wrong-fix-hint genre as F2/F8/F9, now on the Claude path, and it means
`active_unhealthy` alone does not distinguish "unreachable" from "mid-turn".

**Fix:** distinguish "watcher never armed / owner has no watcher record"
from "watcher armed but heartbeat expired", and treat the in-turn gap as an
expected state rather than a health failure.
