# Live findings — 2026-07-27 runtime health review

> Status: historical record — live runtime health review

Development host, installed 0.1.8, standalone Codex `0.145.0`, app-server
launchd pid 73899 (started 2026-07-23T23:03 local), wake bridge running.

## Service layer is healthy; the probe policy has two live green data points

`roundtable doctor` reports the daemon, socket, RPC, version, bridge,
auto-bind queue, hook trust, and setup ownership as OK. The wake log
records `protocol_probe_passed version=0.145.0` at 2026-07-24T06:03 (the
coordinated reload) and again at 2026-07-27T02:37 (a bridge restart).
The uniform floor-plus-probe acceptance policy therefore works against a
release that was never on a validation list, which was its purpose.

## Every live Codex session is unbound; auto-bind has not run since the standalone upgrade

Three Roundtable-launched Codex clients are alive (`MoneyMarket-MacroFinance`
pid 84876, `quant` pid 84092, `roundtable-product` pid 85210, all launched
2026-07-25T23:07–23:08Z). None of them appears in the wake bridge binding
table, so none of them can receive mail. Observables:

- each project has a launcher intent armed within one second of its launch,
  and every one still carries `activeNativeSessionId: null` and
  `lastSessionStartAt: null` — the intents were published and never consumed;
- `.runtime/codex-bind-requests/` has been empty since 2026-07-21, so no
  SessionStart request has been queued since the npm-to-standalone switch;
- the wake log contains exactly two `auto_bind_succeeded` events in its
  entire history, both from the npm `0.144.6` era;
- the only session rollout for these launches
  (`019f9b88…`, cwd `MoneyMarket-MacroFinance`) contains no hook records at
  all;
- the hook itself is correctly configured and reachable: `hooks = true`,
  `hooks.json` `SessionStart[2]` is the roundtable hook with a
  `session_start:2:0` trust entry, the script is executable, all its gates
  (`.roundtable/agents.yaml`, `RT_RUNTIME_DIR` in the app-server plist) are
  satisfied, and `hooks.json` is byte-identical to its backup.

The Claude and Hermes paths, checked in the same session, are healthy and
narrow the fault to Codex. A roundtable-launched Claude seat in
`MoneyMarket-MacroFinance` (owner pid 9708) and a Hermes seat in
`roundtable-product` (owner pid 4570) are both `active_healthy`: their
SessionStart hooks fired, each armed an `rt-wait-inbox` watcher that
inherited the full lease fence, and both heartbeats are seconds old. The
same `hooks`-style integration therefore works on two harnesses and fails
only on Codex, so this is not a roundtable-wide hook regression.

Two further read-only probes localize the fault.

First, the app-server itself reports the hook as live. `hooks/list` for the
project cwd returns `session_start:2:0` with `enabled: true`,
`trustStatus: "trusted"`, `matcher: "startup|resume|clear"`,
`timeoutSec: 5`. Registration, trust, and enablement are therefore all
fine — the daemon knows the hook and considers it runnable.

Second, thread originator attribution changed exactly at the distribution
boundary. Every one of the 59 threads created in the working npm era
(2026-07-20 and 07-21, CLI `0.144.5` and `0.144.6`) carries
`originator: codex-tui`. The only thread created since the standalone
switch — the live `MoneyMarket-MacroFinance` session on 07-25 under
`0.145.0` — carries `originator: roundtable_rt_codex_wake`, which is the
`clientInfo.name` that only our own wake bridge sends in `initialize`
(`bin/_rtcodex.py:1606`). The interactive client is `codex --remote
unix://` and should identify as a TUI; instead the app-server attributes
its thread to the background automation connection.

Leading hypothesis, now narrower: under `0.145.0` a thread on the remote
app-server path is attributed to, and treated as created by, a
non-interactive client, and SessionStart is not dispatched for it. The
alternative — the hook runs but bails inside `resolve_codex_launch_intent`
on the `source`-not-in-{startup,resume} or intent-TTL guard — is not
excluded, because both paths leave `lastSessionStartAt: null`.
Distinguishing them needs one instrumented launch.

Note that the app-server dependency is Roundtable's own design choice, not
a Codex requirement: `bin/_rtlauncher.py` launches every managed Codex seat
as `codex --remote unix://` so the wake bridge has an RPC injection point,
and that is identical for the npm and standalone distributions. Standalone
Codex runs natively without an app-server; a natively launched Codex is
simply outside Roundtable messaging. Distribution detection itself is
correct — `doctor` resolves `distribution=standalone`, the canonical
standalone binary, and a passing probe.

Expected behavior regardless of which branch is true:

1. The launch path must not silently produce a seat that can never receive
   mail. After the launcher arms an intent, something must observe whether
   the intent was consumed and tell the user when it was not.
2. The protocol probe proves the app-server speaks the protocol; it does not
   prove that hook delivery works. Hook execution is the load-bearing part of
   the wake contract and needs its own liveness evidence — this regression
   crossed a harness upgrade boundary that the probe passed cleanly.
3. `doctor` currently renders this state as
   `WARN seat: … active_unhealthy … wake adapter has no heartbeat`, whose fix
   hint is `restart the wake adapter for codex`. That is the wrong diagnosis
   and the wrong remedy: the adapter is running and healthy; the session is
   unbound. An active seat with no binding deserves its own status and a
   fix hint that points at binding.
4. The hook has no failure trace of any kind. Every early return is a silent
   `return 0`. One host-local line per skipped SessionStart, with the reason,
   would have made this a one-minute diagnosis.

## Claude JSON ownership survived the rewrite that destroyed the Hermes YAML block

The same Orca install that broke the comment-fenced Hermes block (see
`findings-2026-07-24.md`) also rewrote `~/.claude/settings.json`, adding ten
of its own hook entries. The owned Roundtable fragments came through intact
and still match the manifest exactly: `SessionStart` and `Stop` groups
calling `rt-wait-inbox` with their args, timeouts, and `asyncRewake`, plus
the three fenced permission rules. Structural JSON ownership tolerates a
harness re-serializing its config; byte-exact YAML fencing does not. That is
direct evidence for expected-behavior item 3 of the Hermes finding.

## A stale binding produces an unbounded rejection loop

The dead `2026-OAI-Build-Week` binding (owner pid 50900, gone) made the
bridge re-attempt a seat heartbeat every ~30 seconds and log the identical
rejection each time, forever: 90,986 `seat_heartbeat_rejected` lines, 29 MB,
97% of the entire wake log. There is no backoff, no deduplication, no log
rotation, and no self-healing of a binding whose owner process is dead.

## `rt-codex-wake unbind` does not affect the running bridge

`unbind` rewrote the state file and cleared the `doctor` FAIL immediately,
but the running bridge kept its in-memory binding and kept logging the
rejection. Only `launchctl kickstart -k gui/$UID/com.roundtable.codex-wake`
stopped it. Either `unbind` should signal the bridge, or its output should
say that a bridge restart is required.

Recovery performed today: `rt-codex-wake unbind` for the Build Week project
followed by a wake-bridge restart. The three live Codex sessions remain
unbound; each must run `rt-codex-wake bind` from inside its own turn, since
`bind` needs `CODEX_THREAD_ID` and the lease environment that only that
session inherits.
